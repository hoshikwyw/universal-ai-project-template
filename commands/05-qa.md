# 05 — QA review

> **Mode:** read-only for production code; tests only if authorized · **Role:** QA Engineer · **Next:** `06-security.md` if security-relevant, otherwise `07-release-check.md`; on `NOT READY`, `bugfix.md` or `04-implement.md`

Act as the QA Engineer (`.agents/qa-engineer.md`). Follow `AGENTS.md`.

## Input
Change under test: `<step ID(s), branch, commit, or PR>`
Authorized to write tests: `<yes / no>`

## Steps
1. Read the acceptance criteria the change covers in `docs/requirements.md`, and read `docs/testing-strategy.md` for test commands, environments, and quality gates.
2. Inspect the implemented change and its tests. Check that every covered `AC-` has at least one test that would fail if the behavior broke.
3. Build a risk-based test matrix that traces each `AC-` to `TC-` items. Include edge cases, error paths, regressions in nearby features, and accessibility where relevant.
4. If authorized, add the missing tests. Never change production code to make a test pass.
5. Run the available, authorized tests and checks. Capture each command and its result.
6. Identify defects, regressions, and coverage gaps, and check the change against the quality gates in `docs/testing-strategy.md`.

## Constraints
- Do not modify production code.
- Never invent test results. Anything not executed is `NOT RUN`, with the reason.
- Do not skip, weaken, or delete failing tests.

## Output
- Test matrix with a result for each case (`PASS` / `FAIL` / `BLOCKED` / `NOT RUN`), and summary counts
- Defects (`BUG-NNN`): severity, steps to reproduce, expected vs. actual, and evidence
- Coverage gaps, quality-gate status, and residual risks
- **Verdict:** `READY` / `NOT READY` / `NEEDS VERIFICATION`, with rationale
- **Next step:** `06-security.md` if the change touches authentication, authorization, user input, sensitive data, dependencies, or CI/CD; otherwise `07-release-check.md`. For defects, use `bugfix.md`.
